Going live on a private server with Docker

Every step from an empty Ubuntu server to the app running publicly over HTTPS through Tailscale Funnel, with commands, a check after each step, and the full config files in the appendix. It covers the open must-do items (M1–M9) from docs/security-report.html; every code-level item there is already fixed and tested.

Read first

The deploy files are in the repo now (2026-11-09), but Docker itself hasn't run them yet: it isn't installed on the development PC. What was tested there:

  • both build contexts, filtered by their .dockerignore: no secrets inside, and the API installs with production packages only (sharp and bcrypt load) while the React app builds;
  • that API copy, run with NODE_ENV=production and TRUST_PROXY=1 behind nginx's headers: it starts with no warnings, the login cookie is Secure, HttpOnly and SameSite=Lax, a plain-http login gets no cookie, and the logs show the client's IP;
  • the compose file parses, and the nginx template's syntax was checked by script (braces, ;, no variables to fill in). nginx itself first runs on the server: step 9 starts with nginx -t.

Every value was checked against the code (ports, paths, env names, the /zit-web/ base, the /api prefix, the Linux binaries in the lock files), and each step ends with a check. Expect one or two small fixes on the first real run.

Compared with your docker-try branch (an earlier attempt before the frontend existed), this setup:

  • adds nginx, which serves the React app, handles HTTPS, and passes /api to Node;
  • no longer publishes port 4586 (the API is reachable only through nginx);
  • gives Mongo a password and an app user that can only use the Zit database;
  • runs Node as a non-root user on Node 24, the same version as your PC;
  • stores pin photos on a volume, so they survive rebuilds;
  • adds health checks;
  • no longer needs environment/ on the server: nothing imports it anymore.

Placeholders used below: zit-server.your-tailnet.ts.net = the server's Tailscale name (the public address) · SERVER_IP = the server's address for SSH (or its Tailscale name) · deploy = the Linux user you work as · /srv/zit = where the code lives on the server. Replace them everywhere.

This file is in .claude/reports/, which git tracks, and the repo is public. It has no secrets, real names or addresses, and it should stay that way: never paste real passwords, connection strings or your real Tailscale names into it.

Your personal projects on the same server use the same Tailscale name on other ports (8443, 10000, …) with tailscale serve, which only devices in your tailnet can reach. Funnel is per port: only port 443 (ZitWeb) is public. See step 7.

Everything is on one address, so the login cookie stays SameSite=Lax and no CORS is needed. The browser calls /api/...; nginx removes /api before passing the request on, because the server's routes have no /api prefix (Vite does the same thing in development).

1

Prepare and secure the server server

A user for you, SSH by key only, a firewall, and automatic security updates.

# as root (or the first user the provider gave you)
adduser deploy
usermod -aG sudo deploy

# on YOUR PC: copy your SSH key to the server, then log in as deploy
ssh-copy-id deploy@SERVER_IP
ssh deploy@SERVER_IP

# key-only SSH, no root login
sudo tee /etc/ssh/sshd_config.d/99-zit.conf >/dev/null <<'EOF'
PasswordAuthentication no
PermitRootLogin no
EOF
sudo systemctl restart ssh

# updates, time zone, firewall
sudo apt update && sudo apt full-upgrade -y
sudo apt install -y unattended-upgrades ufw
sudo dpkg-reconfigure -plow unattended-upgrades     # answer Yes
sudo timedatectl set-timezone Asia/Jerusalem
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
# no 80 / 443: Tailscale Funnel connects out, so no web port is opened on the server
sudo ufw enable

Check

  • Keep your current SSH window open and log in from a second window: ssh deploy@SERVER_IP should work with your key, and ssh root@SERVER_IP should be refused.
  • sudo ufw status shows only OpenSSH.
2

Install Docker server

From Docker's own apt repository (Ubuntu's docker.io package lags behind), with log rotation turned on for every container.

sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list >/dev/null
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# rotate container logs (10 MB × 5 files each), so logs can't fill the disk
sudo tee /etc/docker/daemon.json >/dev/null <<'EOF'
{ "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "5" } }
EOF
sudo systemctl restart docker

# run docker without sudo (log out and back in afterwards)
sudo usermod -aG docker deploy

Check

  • docker run --rm hello-world prints "Hello from Docker!".
  • docker compose version prints v2.x.

Good to know

  • Ports that Docker publishes skip ufw. Only web publishes a port, and only on 127.0.0.1:8080. Never add a ports: line to api or mongo, and never drop the 127.0.0.1, expecting the firewall to block it; it won't. The same applies to your personal projects' containers: publish them as 127.0.0.1:PORT:PORT and reach them through tailscale serve (step 7).
  • Being in the docker group is equivalent to root. Keep it to the deploy user.

Get the code onto the server server

The server pulls from GitHub. It never needs your .env, environment/ or node_modules.

sudo mkdir -p /srv/zit && sudo chown deploy: /srv/zit
git clone https://github.com/elyashiv67/zit-web.git /srv/zit
cd /srv/zit
git checkout v1.0.0          # the tag from step 3

If the repo is private

Create a read-only deploy key on the server and add it under GitHub → repo → Settings → Deploy keys (leave "write access" off). Then clone with the SSH URL:

ssh-keygen -t ed25519 -f ~/.ssh/zit_deploy -N ""
cat ~/.ssh/zit_deploy.pub          # paste into GitHub → Deploy keys
printf 'Host github.com\n  IdentityFile ~/.ssh/zit_deploy\n' >> ~/.ssh/config
git clone git@github.com:elyashiv67/zit-web.git /srv/zit

Check

  • ls /srv/zit shows server/, react/, deploy/, docker-compose.yml.
5

Create the secrets server

Two files, readable only by you. Use openssl rand -hex for database passwords: hex characters never need escaping in a connection string.

cd /srv/zit
cp deploy/api.env.example deploy/api.env
cp deploy/mongo.env.example deploy/mongo.env
chmod 600 deploy/api.env deploy/mongo.env

openssl rand -base64 48     # → SESSION_SECRET in deploy/api.env (new; never reuse the dev one)
openssl rand -hex 24        # → MONGO_INITDB_ROOT_PASSWORD in deploy/mongo.env
openssl rand -hex 24        # → ZIT_APP_PASSWORD in deploy/mongo.env, AND inside DB= in deploy/api.env
nano deploy/api.env  &&  nano deploy/mongo.env

DVR_SECRET: copy it, don't create a new one

The DVR passwords already in the database are encrypted with the DVR_SECRET from your current server/.env. Copy that exact value into deploy/api.env. A new value makes every stored DVR password unreadable. Also store a copy offline (a password manager, or paper in a safe), separate from the backups.

Check

  • ls -l deploy/*.env shows -rw-------.
  • No placeholder text is left: grep -n '<' deploy/*.env prints nothing.
6

Set up Tailscale on the server server + Tailscale admin

Skip the install if the server is already in your tailnet. The machine name becomes the public address, so choose it now.

# install and join your tailnet (prints a login link)
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
tailscale status                       # the server is listed

Then in the Tailscale admin console (login.tailscale.com/admin):

  • Machines → the server → Edit machine name, e.g. zit-server. The public address becomes https://zit-server.your-tailnet.ts.net. Your personal projects share that name, on other ports.
  • Machines → the server → Disable key expiry. Otherwise the server drops off Tailscale after a few months and the site goes down until you log it in again.
  • DNS: MagicDNS and HTTPS Certificates on. Funnel needs both.
  • Funnel itself is allowed per machine in the access controls (the funnel node attribute). The first tailscale funnel command in step 7 prints a link that adds it for you.

Optional: SSH only through Tailscale

Then no port at all is open to the internet. First check that ssh deploy@zit-server works over Tailscale from a second window, then:

sudo ufw allow in on tailscale0 to any port 22 proto tcp
sudo ufw delete allow OpenSSH

Keep the provider's web console handy as a way back in, in case Tailscale is ever down.

Check

  • tailscale status on your PC lists the server under its new name.
  • The admin console shows "Expiry disabled" for the server.
7

Open ZitWeb to the public with Funnel server

Funnel gives port 443 of the Tailscale name a trusted certificate and passes requests to nginx on 127.0.0.1:8080. Tailscale renews the certificate on its own.

sudo tailscale funnel --bg 8080        # first time: open the printed link to allow Funnel, then run it again
tailscale funnel status
# https://zit-server.your-tailnet.ts.net (Funnel on)
# |-- / proxy http://127.0.0.1:8080

Until step 9 starts the containers, the address answers 502. That's expected. --bg keeps the setting across reboots.

Your personal projects: tailnet only

Funnel is per port, and only 443, 8443 and 10000 can be public. ZitWeb takes 443. Put each personal project on another port with serve (not funnel), so only your own devices reach it:

# a project listening on 127.0.0.1:3000 → https://zit-server.your-tailnet.ts.net:8443 (tailnet only)
sudo tailscale serve --bg --https=8443 http://127.0.0.1:3000
# another one on 127.0.0.1:5000 → :10000
sudo tailscale serve --bg --https=10000 http://127.0.0.1:5000
tailscale serve status                 # "Funnel on" must appear only next to :443

In their own docker-compose.yml files, publish them as "127.0.0.1:3000:3000", never "3000:3000": a plain published port is open to the internet on the server's IP, and ufw doesn't stop it.

Careful: tailscale serve reset and tailscale funnel reset remove every mapping, including ZitWeb's. To remove one, repeat its command with off at the end, e.g. sudo tailscale serve --https=8443 off.

Check

  • tailscale funnel status shows Funnel on for :443 → http://127.0.0.1:8080 and nothing else public.
  • A new Funnel name can take up to ~10 minutes before it works on the internet.
8

Start the database and move the data server

Start Mongo alone, copy the current data into it, then copy the pin photos. Login sessions are not copied: everyone logs in once on the new server, which is expected because the session secret is new.

cd /srv/zit
docker compose up -d mongo
docker compose ps                      # wait until mongo is "healthy"

# 1) database: Atlas → the new Mongo. In Atlas → Network Access, temporarily allow SERVER_IP.
read -rs ATLAS_URI                     # paste the Atlas connection string (not saved in shell history)
docker run --rm mongo:8.0 mongodump --uri "$ATLAS_URI" --db Zit --excludeCollection sessions --archive --gzip > /tmp/zit.archive.gz
docker compose exec -T mongo sh -c 'mongorestore -u "$MONGO_INITDB_ROOT_USERNAME" -p "$MONGO_INITDB_ROOT_PASSWORD" --authenticationDatabase admin --archive --gzip' < /tmp/zit.archive.gz
shred -u /tmp/zit.archive.gz; unset ATLAS_URI

# 2) photos: from the machine the server runs on today (its server/uploads/pins folder)
#    on that machine:  scp -r server/uploads/pins deploy@SERVER_IP:/tmp/pins
docker compose up -d api               # creates the uploads volume (and its pins/ folder)
# copy with a throwaway container: api has no Linux capabilities, so even its root can't chown.
# 1000 is the "node" user the API runs as
docker run --rm -v zit_uploads:/data -v /tmp/pins:/src:ro alpine sh -c 'cp -a /src/. /data/pins/ && chown -R 1000:1000 /data'
rm -rf /tmp/pins

Option A staying on Atlas

  • Delete the mongo service and the mongo-data volume from docker-compose.yml, and the depends_on: mongo lines from api.
  • In Atlas → Network Access, allow only SERVER_IP, and remove 0.0.0.0/0 if it's there.
  • In Atlas → Database Access, create a user with readWrite on Zit only, and put its connection string in DB=.
  • The free Atlas tier (M0) has no backups, so step 12's script backs it up for you.
  • Only the photos need to be copied.

Check

docker compose exec mongo sh -c 'mongosh -u "$MONGO_INITDB_ROOT_USERNAME" -p "$MONGO_INITDB_ROOT_PASSWORD" --quiet --eval "
  const z = db.getSiblingDB(\"Zit\");
  printjson({users: z.users.countDocuments(), pins: z.pins.countDocuments(), units: z.units.countDocuments(), roles: z.roles.countDocuments()})"'
docker compose exec api sh -c 'ls /data/uploads/pins | wc -l'    # = number of pins that have photos

The counts should match Atlas. Then remove SERVER_IP from Atlas's network access if you're leaving Atlas.

The first build takes a few minutes: it installs packages and builds the React app.

docker compose build

  • If api keeps restarting, see Troubleshooting. The first log lines name the bad setting without printing its value.

Check it end to end server + phone

Proof that HTTPS, headers, the proxy, cookies and closed ports all work, before real users arrive.

U=https://zit-server.your-tailnet.ts.net
curl -sI $U | grep -iE '^(HTTP|location)'          # 302, location: /zit-web/ (relative, so it stays https)
curl -s $U/api/health                              # {"status":"ok"}
curl -sI $U/zit-web/ | grep -iE 'strict-transport|content-security|x-content-type'
curl -sI $U/zit-web/pins | head -1                 # 200 (a page refresh inside the app works)

# from a machine OUTSIDE your tailnet, against the server's own public IP: nothing but (maybe) 22 is open
nmap -Pn -p 22,80,443,4586,8080,27017 SERVER_PUBLIC_IP
# and the personal projects are not public (Tailscale off on that machine): this must fail
curl -m 10 -sI https://zit-server.your-tailnet.ts.net:8443

The real user IP (important for the login rate limit)

Log in once from your phone over mobile data, then run docker compose logs api | tail -5. The lines must start with your phone's public IP. If every line shows the same 172.x.x.x or 127.0.0.1, the client's IP isn't getting through, and the login limit would treat all users as one person: a few wrong passwords from one user would lock everyone out. Stop there and send Claude a few of those log lines.

Check on a phone, over mobile data (not Wi-Fi), with the Tailscale app off

  • Open https://zit-server.your-tailnet.ts.net. It redirects to /zit-web/ with a lock icon and no certificate warning.
  • Log in, then open the pins page: the map tiles appear.
  • Open a pin and reveal its DVR password. If it shows correctly, DVR_SECRET is right.
  • Upload a photo, then open it.
  • Refresh the page: you stay logged in.
  • Log out, then press Back: you get the login page, not data.
  • On a PC (DevTools → Application → Cookies): zit.sid is HttpOnly, Secure and SameSite=Lax.

Clean up the data the app (admin)

Leftovers from development.

  • In ניהול → משתמשים, delete the test accounts created during development (security report M6).
  • Give the admin a long password (12+ characters). New passwords must be at least 8 characters.
  • Nothing to do for older passwords: each user's stored hash is upgraded to the stronger setting (bcrypt cost 12) automatically at their next login.

Check

  • The users list shows only real people, and at least one admin. The server won't let you remove the last admin.
12

Backups (and a test restore) server

A nightly copy of the database and the photos, kept for 14 days. Copy them off the server too: a backup on the same disk doesn't survive losing that disk.

chmod +x /srv/zit/deploy/backup.sh
sudo /srv/zit/deploy/backup.sh && ls -lh /srv/zit-backups     # run once by hand
sudo crontab -e
# add this line: every night at 02:30
30 2 * * * /srv/zit/deploy/backup.sh >> /var/log/zit-backup.log 2>&1

Test a restore once now, and then every few months. This loads the backup into a separate database, so the live data isn't touched:

cd /srv/zit
docker compose exec -T mongo sh -c 'mongorestore -u "$MONGO_INITDB_ROOT_USERNAME" -p "$MONGO_INITDB_ROOT_PASSWORD" --authenticationDatabase admin --archive --gzip --nsFrom "Zit.*" --nsTo "ZitRestoreTest.*"' < /srv/zit-backups/db-YYYY-MM-DD.archive.gz
# compare counts with step 8's check (use "ZitRestoreTest"), then remove the copy:
docker compose exec mongo sh -c 'mongosh -u "$MONGO_INITDB_ROOT_USERNAME" -p "$MONGO_INITDB_ROOT_PASSWORD" --quiet --eval "db.getSiblingDB(\"ZitRestoreTest\").dropDatabase()"'
tar tzf /srv/zit-backups/uploads-YYYY-MM-DD.tgz | head      # the photos are in the archive

Off-server copy

Copy /srv/zit-backups to another machine every night (rsync over SSH, or an encrypted cloud bucket). The backups contain personal data and the encrypted DVR passwords: keep them only where the app's data may be. Keep DVR_SECRET somewhere else; together with a backup, it can read every DVR password.

13

Retire GitHub Pages and keep it running GitHub + server

The old public copy of the app goes away; then the routine for updates.

  • GitHub Pages: repo → Settings → Pages → unpublish, then delete the gh-pages branch. That old build is still public there. Afterwards the predeploy/deploy scripts and public/404.html can go; Claude can make that small code change.
  • Deploying a new version: 
    cd /srv/zit
git fetch --tags && git checkout v1.1.0
docker compose build && docker compose up -d
docker compose ps
    Run the tests on your PC before tagging. Users may need to refresh once; index.html is never cached, so they get the new version.
  • Rolling back: git checkout v1.0.0 && docker compose build && docker compose up -d. The data is untouched: the app has no database migrations.
  • Monthly: run npm audit on your PC (server/ and react/), and update the base images with docker compose build --pull. Check disk space (df -h, docker system df) and the backup log, and delete old images with docker image prune.
  • Monitoring: a cron job or an uptime service polling https://zit-server.your-tailnet.ts.net/api/health (it only says whether the DB is up). Tailscale renews the certificate automatically. After a server reboot, tailscale funnel status should still show Funnel on, and the containers restart on their own.
  • Tailscale: keep it updated with the server's apt updates. If the site is down but curl -sI http://127.0.0.1:8080/zit-web/ on the server works, the problem is Funnel: check tailscale status and tailscale funnel status.

Appendix: the files

The same files are in the repo; the repo is the source of truth. Only the .example files get copied and filled in, and only on the server (step 5).

docker-compose.yml (repo root) 
# ZitWeb: Tailscale Funnel (https, on the host) → nginx (web) → Node API (api) → MongoDB (mongo).
# Step-by-step: .claude/reports/deployment-guide.html. Secrets live in deploy/*.env on the server only.
name: zit

services:
  web:
    build: ./react
    ports:
      # this machine only: the public way in is Tailscale Funnel (tailscale funnel --bg 8080).
      # Docker-published ports skip ufw, so never drop the 127.0.0.1.
      - "127.0.0.1:8080:80"
    volumes:
      - ./deploy/nginx.conf.template:/etc/nginx/templates/default.conf.template:ro
    depends_on:
      api:
        condition: service_healthy
    restart: unless-stopped

  api:
    build: ./server
    env_file: ./deploy/api.env
    volumes:
      - uploads:/data/uploads
    init: true                 # proper signal handling / zombie reaping for node as PID 1
    mem_limit: 1g              # photo compression peaks around 600MB
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL                    # node needs no Linux capabilities (port 4586 is above 1024)
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://localhost:4586/health').then(r => process.exit(r.ok ? 0 : 1), () => process.exit(1))"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 20s
    depends_on:                # Option A (Atlas): delete these 3 lines
      mongo:

deploy/nginx.conf.template 
# nginx for ZitWeb, used by the "web" container (docker-compose.yml).
# HTTPS is handled by Tailscale Funnel on the host: https://<server>.<tailnet>.ts.net → http://127.0.0.1:8080 → here.
# The file lands in /etc/nginx/conf.d/default.conf, inside nginx's http { } block.

# The user's real IP: tailscaled (on the host) adds X-Forwarded-For, and its requests reach this container from
# Docker's bridge gateway. Only those addresses are trusted to set it; walking from the right, the first untrusted
# address is the client, so a value the client sends itself is ignored. Port 8080 is published on 127.0.0.1 only,
# so every connection comes through a Docker gateway; Docker picks its networks from these private ranges
# (more projects on the server can push it from 172.x to 192.168.x or 10.x).
set_real_ip_from 172.16.0.0/12;
set_real_ip_from 192.168.0.0/16;
set_real_ip_from 10.0.0.0/8;
set_real_ip_from 127.0.0.1;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

# Built files under /zit-web/assets/ have a content hash in their name, so they can be cached for a year.
# Everything else in the app (index.html, icons, manifest) is revalidated, so a new version shows up at once.
# After try_files falls back to index.html, $uri is /zit-web/index.html, so the fallback gets "no-cache".
map $uri $zit_cache_control {
    ~^/zit-web/assets/  "public, max-age=31536000, immutable";
    default             "no-cache";
}

server {
    listen 80;
    server_name _;
    server_tokens off;
    # nginx only sees http (Tailscale did the https part), so redirects must stay relative ("Location: /zit-web/"),
    # or the browser would be sent to http://
    absolute_redirect off;

    client_max_body_size 1m;

    location = / { return 302 /zit-web/; }
    location = /zit-web { return 301 /zit-web/; }

    # the React app. NOTE: add_header inside a location replaces the server-level ones, so all are listed here
    location /zit-web/ {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /zit-web/index.html;

        gzip on;
        gzip_types text/css application/javascript image/svg+xml application/json application/manifest+json;

        add_header Cache-Control $zit_cache_control always;
        add_header Strict-Transport-Security "max-age=31536000" always;
        add_header X-Content-Type-Options "nosniff" always;
        # OSM's tile servers require a referrer, so not "no-referrer"
        add_header Referrer-Policy "strict-origin-when-cross-origin" always;
        # the pin form asks for the phone's location; photos come from a file input, which needs no camera permission
        add_header Permissions-Policy "camera=(), microphone=(), geolocation=(self)" always;
        add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://tile.openstreetmap.org https://*.tile.openstreetmap.org; font-src 'self'; connect-src 'self'; manifest-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'" always;
    }

    # the API: "/api/x?y" → "http://api:4586/x?y". helmet adds the API's own security headers.
    location /api/ {
        # Docker's DNS, asked again every 10s: a rebuilt api container gets a new address, and nginx follows it
        # (a fixed "proxy_pass http://api:4586/" would keep the old address and answer 502 until a restart)
        resolver 127.0.0.11 valid=10s ipv6=off;
        set $api_upstream api:4586;
        rewrite ^/api/(.*)$ /$1 break;
        proxy_pass http://$api_upstream;

        proxy_http_version 1.1;
        proxy_set_header Host $host;
        # one hop in front of Node (this nginx), matching TRUST_PROXY=1. $remote_addr is the real client IP from above.
        proxy_set_header X-Forwarded-For $remote_addr;
        # users only reach this port through Funnel's https (it listens on 127.0.0.1 only), so the login cookie is Secure
        proxy_set_header X-Forwarded-Proto https;

        # photo uploads: up to 10 × 25MB per request, phones can be slow
        client_max_body_size 260m;
        client_body_timeout 300s;
        proxy_send_timeout 300s;
        proxy_read_timeout 300s;
    }

    # nothing else is served
    location / { return 404; }
}

deploy/backup.sh 
#!/bin/sh
# Nightly backup of the database and the pin photos, kept 14 days.
# Run as root from cron (deployment guide, step 12). Copy /srv/zit-backups off the server as well.
set -eu
cd /srv/zit
DIR=/srv/zit-backups
DAY=$(date +%F)
umask 077
mkdir -p "$DIR"

# database, without login sessions. Option B (container):
docker compose exec -T mongo sh -c 'mongodump -u "$MONGO_INITDB_ROOT_USERNAME" -p "$MONGO_INITDB_ROOT_PASSWORD" --authenticationDatabase admin --db Zit --excludeCollection sessions --archive --gzip' \
  > "$DIR/db-$DAY.archive.gz.part"
# Option A (Atlas): put ATLAS_BACKUP_URI=... in /srv/zit/deploy/backup.env (chmod 600), then use these two lines
# instead of the docker compose line above:
#   . /srv/zit/deploy/backup.env
#   docker run --rm mongo:8.0 mongodump --uri "$ATLAS_BACKUP_URI" --db Zit --excludeCollection sessions --archive --gzip > "$DIR/db-$DAY.archive.gz.part"
mv "$DIR/db-$DAY.archive.gz.part" "$DIR/db-$DAY.archive.gz"

# photos (the "uploads" volume of the "zit" compose project)
docker run --rm -v zit_uploads:/data:ro alpine tar czf - -C /data . > "$DIR/uploads-$DAY.tgz.part"
mv "$DIR/uploads-$DAY.tgz.part" "$DIR/uploads-$DAY.tgz"

# keep two weeks (and drop half-written files from a failed night)
find "$DIR" -type f -mtime +14 -delete
find "$DIR" -type f -name '*.part' -mmin +60 -delete
echo "$(date -Is) backup ok: $(du -sh "$DIR" | cut -f1)"
